# F16-T09 · Perf & thermal guard

> Plan for task 9 of [F16](../F16-live-edge-detection.md). The task that makes the
> feature safe to leave on.

## Goal
Continuous per-frame work on a preview is the classic source of heat and battery
drain (F16 Risks). Detection must bound its own cost and switch itself off —
silently (locked decision #4) — when it cannot keep up, leaving the F15-T12 box
behind with no user-visible change.

## Design decisions

1. **Budget, stated up front:** a detection must complete within about **120 ms**
   (the T04 throttle interval) and the preview must never drop frames because of
   it. The numbers to record in the doc are the measured p50/p95 of
   `DetectDocumentEdges` on the T10 device, plus the isolate round-trip.
2. **The rule for switching off:** keep the last `windowSize` (default 10)
   detection durations; disable if the **p50 exceeds `budget`** (default 120 ms)
   **or** if `consecutiveLate` (default 5) detections each exceed `2 x budget`.
   Two conditions, because a uniformly slow phone and a phone that has just
   started thermally throttling look different.
3. **Disabling is terminal for the session, and silent.** On disable: stop the
   frame stream, emit a ready state with `quad: null`, and do not retry within
   this camera session. A re-`start()` (app resumed, screen re-entered) gets a
   fresh budget — a phone that has cooled down deserves another chance, and the
   cost of being wrong is only the static box. **No toast, no banner, and no log
   beyond a non-content debug line.**
4. **Isolate strategy is decided here.** Measure the `Isolate.run` spawn cost on
   the device first. If it is a meaningful share of the budget (it usually is, at
   a few ms plus message copies), replace it with a **persistent worker
   isolate**: spawn once on `startFrameStream`, keep a `SendPort`, ship frames as
   `TransferableTypedData`, kill it on `stopFrameStream`. T03's split between the
   algorithm and its wrapper means this touches only
   `dart_document_edge_detector.dart` and its thin wrapper test.
5. **Shutter path stays jank-free.** T04/T07 already stop the stream before
   `takePicture`; add a test that no detection is in flight when the shutter path
   starts, and verify on-device that the shutter feels identical with detection
   on and off.
6. **The guard is internal state, not a user setting.** No entry in Settings —
   F16 is a guidance layer, and a toggle would invite the user to diagnose
   something they should never see (locked decision #4). A manual kill-switch, if
   ever wanted, is a new task.

## Steps
1. `DetectionBudget`: `record(Duration)`, `bool get shouldDisable`, `reset()`,
   named thresholds with defaults, injectable clock for tests.
2. Cubit: time each detection in `_onFrame` with a `Stopwatch`, feed the budget,
   act on `shouldDisable` (stop the stream, publish `null`, latch a
   `_detectionDisabled` flag that `_onFrame` checks first). Reset in `start()`.
3. Only add a `detectionEnabled` field to the state if a test or the screen
   actually needs it — the screen already renders the static box for
   `quad: null`, so prefer not to add state with no consumer.
4. Device measurement pass, then fill the budget table in the F16 doc.
5. Isolate decision per #4, with before/after numbers in the same table.

## Tests
- `DetectionBudget`: under budget never disables; a p50 over budget across the
  window disables; 5 consecutive very-late frames disable; a single outlier in an
  otherwise fast window does **not** disable; `reset()` clears both conditions.
- Cubit: a slow fake detector stops the stream and the quad goes `null` after the
  threshold — and **no** `CameraCaptureError` is ever emitted.
- Cubit: after auto-disable, further frames are ignored without invoking the
  detector at all.
- Cubit: `start()` after a disable re-enables detection.
- Existing capture/cleanup tests still green.
