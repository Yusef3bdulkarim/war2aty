# F16-T05 · Frame → preview coordinate mapping

> Plan for task 5 of [F16](../F16-live-edge-detection.md). Pure geometry, pure
> functions, heavily tested — this is where a silent 90° bug would live.

## Goal
The detector's quad is in **sensor space**. The overlay draws in **preview
space** — the same space `_measureGuideBox` already works in (fractions of the
live preview's rendered rect). This task is the transform between them.

## Files

**New**
- `lib/features/capture/presentation/frame_preview_mapper.dart` — a small class
  with one pure static entry point. Presentation, not domain: it is about how a
  widget renders, and it needs no Flutter types beyond what it can take as plain
  doubles.
- `test/features/capture/frame_preview_mapper_test.dart`

**Modified**
- `lib/features/capture/domain/entities/camera_frame.dart` (T02) — add
  `sensorOrientation` (int degrees) and `isMirrored` (bool) if not already
  carried; `PlatformCameraService` fills them from `CameraDescription`
  (`sensorOrientation`, `lensDirection == front`). Prefer carrying them on the
  frame over re-reading the controller from presentation.

## Design decisions

1. **One entry point:**
   `DocumentQuad mapToPreview(DocumentQuad sensorQuad, {required int
   sensorOrientation, required bool isMirrored, required double frameAspect,
   required double previewAspect, required PreviewFit fit})`
   → a quad in 0..1 of the preview rect. Everything is a plain number so the
   function is trivially testable and has no widget dependency.
2. **Composition order is fixed and documented:** rotate (sensor orientation) →
   mirror (front lens) → fit-correct (aspect difference between the rotated frame
   and the preview rect). Any other order is wrong; the doc comment says so.
3. **Rotation is exact, on normalised coordinates:** 90° → `(x, y) → (1 - y, x)`,
   180° → `(1 - x, 1 - y)`, 270° → `(y, 1 - x)`, plus the aspect swap for 90/270.
   Implemented as a `switch` over `sensorOrientation % 360`, defaulting to 0 for
   an unexpected value (degrade, never throw — locked decision #4).
4. **Mirroring** is `x → 1 - x` after rotation, applied only when `isMirrored`.
   The app is back-camera only today, so this path is defensive; test it anyway,
   because the cost of being wrong later is a silently flipped overlay.
5. **The fit step** accounts for `CameraPreview` painting the feed at the
   controller's aspect ratio inside the rect the screen gives it. The screen
   already wraps the preview in `Center(KeyedSubtree(key: _previewKey, …))` and
   measures **that render box**, so in practice the measured rect *is* the
   painted feed and the fit correction is the identity. Implement it anyway as an
   explicit `PreviewFit { contain, cover }` with `contain` as the default, so the
   assumption is visible and testable instead of implicit. If T10 shows the
   preview is actually cropped (`cover`), only this one function changes.
6. **No `dart:ui` needed** — the mapper works on `UnitPoint`/`DocumentQuad` from
   T02 and doubles.
7. **The mapper does not measure anything.** Measurement stays in
   `_CameraCaptureScreenState`, reusing `_previewKey` exactly as
   [`_measureGuideBox`](../../../lib/features/capture/presentation/screens/camera_capture_screen.dart)
   does — the task's "shares the preview-rect measurement" requirement. Extract
   the shared `previewRect` read into a tiny private helper the two call sites
   both use; do not duplicate the render-box logic.

## Steps
1. Add `sensorOrientation`/`isMirrored` to `CameraFrame` and fill them in
   `PlatformCameraService` from the chosen `CameraDescription`.
2. Write `frame_preview_mapper.dart` with the three composable private
   transforms and the public `mapToPreview`.
3. In `camera_capture_screen.dart`, factor out `Rect? _previewRect()` from
   `_measureGuideBox` and use it in both places. No behaviour change; the
   existing screen tests must stay green untouched.
4. Tests.

## Tests (`frame_preview_mapper_test.dart`)
A named fixture quad (asymmetric on purpose — a quad with a distinct TL — so a
180° error cannot pass), then:
- Identity at `sensorOrientation: 0`, not mirrored, equal aspects.
- Each of 90 / 180 / 270: assert the exact expected corner coordinates, and that
  the result is still ordered TL/TR/BR/BL after mapping.
- 90 + mirrored, 270 + mirrored: the mirror is applied *after* the rotation
  (a test that fails if the order is swapped).
- Aspect mismatch with `contain`: a 4:3 frame into a 3:4 preview rect →
  letterboxed, corners inset on the correct axis and still in 0..1.
- Aspect mismatch with `cover`: corners may fall outside 0..1 → assert they are
  **not** silently clamped (the caller decides; clamping is `boundingRect`'s job).
- Unexpected orientation (e.g. 45) → treated as 0, no throw.
- Round-trip sanity: mapping by 90 four times returns the original quad.
