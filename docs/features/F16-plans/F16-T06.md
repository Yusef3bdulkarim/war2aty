# F16-T06 · Guide box follows the quad

> Plan for task 6 of [F16](../F16-live-edge-detection.md). The visible half of
> the feature — and the task that quietly decides how easy T08 is.

## Goal
`ViewfinderFrame` draws the detected quad instead of the static box when there is
one, moves smoothly between detections, and falls back to today's box otherwise
(locked decision #4).

## Design decisions

1. **One widget, one optional parameter.** `ViewfinderFrame({required frameKey,
   this.quad})`, `quad` being a `DocumentQuad?` already in **preview space**
   (T05 did the mapping; the widget does no geometry beyond scaling by its own
   size). `quad == null` → today's exact `resolveSize`-centred box, untouched.
2. **`frameKey` moves onto the quad's bounding box when a quad is shown.** This
   is the key decision of the task: keep `frameKey` on a `Positioned` sized to
   `quad.boundingRect` scaled into the preview rect, so
   [`_measureGuideBox`](../../../lib/features/capture/presentation/screens/camera_capture_screen.dart)
   keeps working **verbatim** and T08 becomes verification rather than new
   geometry. Do not introduce a second key or a parallel measurement path.
3. **Smoothing lives in the widget, holding lives in the cubit.**
   - Widget: an `AnimationController` (~180 ms, `Curves.easeOut`) driving
     `DocumentQuad.lerpTo` between the previously-rendered quad and the newest
     one, updated in `didUpdateWidget`. Cheap, and it is a pure rendering concern.
   - Cubit (T07): the "a detection dropped out — hold the last quad" grace
     window. That is policy with a time constant, so it is testable in a cubit
     test rather than a widget test.
   The widget therefore never invents a quad; it only animates toward what it is
   given, and animates back to the static box when handed `null`.
4. **Corner brackets, same visual language as today.** Reuse `_bracket` (34),
   `_bracketStroke` (3), and `AppColors.of(context).mint`. The brackets are drawn
   along each corner's two *actual* edge directions, so they rotate with the
   quad — a `CustomPainter`, since four rotated L-shapes are not expressible with
   `Align`/`Border`.
5. **The scan line and the faint fill stay** — the design's identity. Clip them to
   the quad path when a quad is shown (`Path` from the four corners), so the fill
   follows the paper instead of a rectangle behind it.
6. **Never state-by-colour-alone** (design system rule). The mint brackets change
   *shape* (they sit on the paper's real corners) rather than merely changing
   colour, and the existing Arabic hint text stays. Do not add a green/red
   "detected" tint as the only signal.
7. **`StatefulWidget` now** (it already hosts the `_ScanLine` child, but the frame
   itself becomes stateful for the animation controller). Controller created in
   `initState`, disposed in `dispose` (CLAUDE.md §B.8) — never in `build`.
8. **`const` everywhere it still applies**; the painter's `shouldRepaint`
   compares the quad, so a null-quad frame does not repaint per tick beyond the
   existing scan line.

## Steps
1. Make `ViewfinderFrame` stateful; add the controller + `_displayedQuad` /
   `_targetQuad` fields and the `didUpdateWidget` retarget.
2. Split `build` into `_buildStaticBox(constraints)` (today's code, moved
   verbatim) and `_buildQuad(constraints, quad)`.
3. Write the painter: quad path, faint fill, 1.5 px hairline outline, four
   rotated mint L-brackets, clipped scan line.
4. Put `frameKey` on the bounding-rect `Positioned` in the quad branch (decision
   #2) — and add a comment there naming T08, so the coupling is discoverable.
5. Handle the `null` transition: animate the current quad toward the static box's
   rect-as-quad, then hand rendering back to the static branch, so it fades
   rather than snapping.
6. Tests.

## Tests (`viewfinder_frame_test.dart`)
Existing 5 tests stay. Add:
- `quad == null` renders exactly the static box (golden-free: assert the
  `frameKey` render box size equals `resolveSize(preview)` — the existing
  assertion style).
- With a quad, the `frameKey` box equals the quad's bounding rect in preview
  coordinates (this is the assertion T08 depends on).
- Changing the quad animates: pump 1 frame → the rendered quad is *between* old
  and new; pump past the duration → it equals the new one. (Never
  `pumpAndSettle` — the scan line animates forever; the existing tests already
  document this.)
- quad → null → the static box is showing again after the animation.
- **RTL**: wrapped in `Directionality(TextDirection.rtl)`, the quad is drawn at
  the same physical coordinates (it is camera space, not text space — a mirrored
  overlay would be a bug).
- **Large Text**: `TextScaler.linear(2.0)` does not change the quad geometry.
- **High Contrast**: rendered with `AppColors.highContrast`, the brackets resolve
  to that palette's mint (same lookup the existing widgets use).
- No exception when the quad is degenerate/near-zero area (defensive: draw
  nothing, fall back to the static box).
